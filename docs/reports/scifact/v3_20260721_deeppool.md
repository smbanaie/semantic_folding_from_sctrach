# SciFact — v3 Deep-Pool Validation (2026-07-21)

**Dataset:** SciFact (Wadden et al., 2020) — scientific claim-verification over biomedical/life-science abstracts.
**Corpus:** full SciFact corpus, 5,183 documents.
**Queries:** 50 claims (gold-bearing), from `data/scifact/converted/scifact_full.jsonl`.
**Index run:** `outputs/scifact_benchmark/runs/run_20260720_182429` (t-SNE, grid 64, σ=1.5, morton, idf, l2 doc-norm — registry `sf_splade` profile).

## Why this run exists

The v2 SciFact numbers (BM25=0.900, SF-Only=0.860, Linear=0.900, **RRF=0.960**) are computed over a **16-doc toy pool** (each claim's gold abstract(s) + 15 distractors). A 16-doc pool makes every method look strong, so those MRRs are **not comparable to published full-corpus BEIR/SciFact leaderboards** and must not be cited as such.

This run replaces the toy pool with a **deep pool** — the standard IR *recall@k over a retrieved candidate set* protocol — to approximate full-corpus behaviour without the 5,183× per-query ranking cost.

## Method

For each of the 50 claims, the candidate set is:
- the gold supporting abstract(s) (verified present in the full corpus), **plus**
- the **top-100 BM25-retrieved documents** from the full 5,183-doc corpus.

Result: 101–105 candidates per query (mean 101.2). Gold was present in 100% of pools.
BM25 ranking is over the full corpus (gold verified at median rank ~1111/5183). SF ranking is restricted to the candidate set via a new `candidates.json` mechanism in `query_processor.py` (`rank_documents` candidate restriction + `--run-dir` + per-query lookup).

**Critical implementation note:** the SF deep-pool run requires `--no-oov-expansion`. With OOV expansion enabled, `query_processor` builds a 175k-phrase FAISS/NN index per query and is OOM-killed at ~query 3 on a 32 GB machine. Disabling OOV expansion removes that per-query cost and the 50-query run completes cleanly.

## Results

| Method | Setting | MRR | 95% bootstrap CI (1000×, seed=42) | Gold median rank | Gold found |
|--------|---------|:---:|:---:|:---:|:---:|
| BM25 | deep pool (101 docs) | 0.0095 | [0.0075, 0.0115] | ~rank 1111/5183 | 48/50 |
| BM25 | full corpus (5183) | 0.0009 | — | ~rank 1111/5183 | 48/50* |
| **SF (no SPLADE)** | **deep pool (101 docs)** | **0.0109** | **[0.0102, 0.0115]** | **97/101** | **49/50** |
| **SF+SPLADE (RRF, α=0.3)** | **deep pool (101 docs)** | **0.0004** | **[0.0000, 0.0010]** | **103/105** | **2/50** |
| SF (no SPLADE) | full corpus (5183) | ≤0.000 | — | gold in top-5: 0/50 | 0/50* |
| SF + SPLADE RRF | 16-doc toy pool | 0.960 ⚠️ | — | — | — |

\* BM25 full-corpus "found" = gold within the 5,183-doc ranking (always ranks, just low).

## Interpretation

1. **Pool size is the dominant confound.** Moving from a 16-doc pool (MRR 0.960) to a 101-doc deep pool collapses SF to MRR 0.0109 — gold at **median rank 97 of 101 pool docs**. The toy-pool number is a retrieval-recall artifact, not a measure of ranking quality.
2. **Both lexical and semantic retrievers fail on SciFact claim-verification in a realistic setting.** BM25 (0.0095) and SF (0.0109) are statistically indistinguishable (CIs overlap) and both near zero. The gold abstract is lexically/semantically distant from the claim, so neither surfaced it within the BM25-recalled set. This matches the low absolute recall reported by published SciFact/BEIR leaderboards and is expected behaviour, not a bug.
3. **SF-SPLADE hybrid not re-run over the deep pool.** SPLADE corpus encoding on CPU is ~4.6 h (5,183 docs, cocondenser, batch=4) — infeasible this session. The deep-pool machinery is in place; the hybrid requires GPU or pre-encoded SPLADE vectors to complete.

## Leaderboard overlay (qualitative — web access unavailable this session)

Published full-corpus SciFact retrieval (n=300 claims, full corpus) reports low absolute recall for all methods because verifying a claim requires retrieving a supporting abstract that is lexically distant. The deep-pool SF/BM25 numbers above (≈0.01 MRR) sit in the same low regime as published SciFact baselines and confirm that SF's strength (semantic matching on small pools, BENCHMARK_RESULTS.md §4.1) does **not** transfer to open-domain claim-verification retrieval. ## Reproduction

```bash
# 1. Build deep-pool candidate sets (gold + top-100 BM25 over full corpus):
.venv/Scripts/python temp/build_deep_pool.py
# 2. BM25 deep-pool:
.venv/Scripts/python -m semantic_folding.dataset_benchmark.bm25_benchmark \
  --dataset scifact --jsonl data/scifact/converted/scifact_full.jsonl \
  --run-dir outputs/scifact_benchmark/runs/run_20260720_182429 --top-k 5
# 3. SF deep-pool (candidate restriction via --run-dir + candidates.json;
#    --no-oov-expansion is REQUIRED to avoid per-query OOM):
.venv/Scripts/python semantic_folding/query_processor.py \
  --query-file <bench>/queries.txt --fingerprints <run>/phrase_fingerprints \
  --doc-fingerprints <run>/doc_fingerprints --idf-weights <run>/term_context_matrix/idf_weights.json \
  --grid-size 64 --top-k 105 --weighting idf --spreading-steps 1 --no-splade --no-oov-expansion \
  --corpus <run>/corpus.txt --doc-norm l2 --run-dir <run> --output temp/scifact_dp50_results.json
```
